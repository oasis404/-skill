# 第三方集成与接口

## 两个方向先分清楚

对接前最要紧的是先确认数据往哪个方向流，两者的实现路径完全不同：

| 方向 | 场景 | 实现方式 |
|------|------|---------|
| **外部系统 → EKP** | 业务系统自动发起一张 OA 单据 | 调用 EKP 的启动流程接口 |
| **EKP → 外部系统** | 流程审批通过后回写业务系统数据 | 机器人节点 + TIC 第三方集成中心 |

## 一、TIC 第三方集成中心（EKP → 外部系统）

机器人节点要调外部接口，靠的是集成中心。配置顺序固定为五步：

1. **服务配置**：注册外部系统的接口地址。SOAP 服务填 WSDL 地址，REST 服务填接口 URL 与认证方式
2. **函数配置**：从服务里挑出要用的具体方法，绑定成一个"函数"
3. **数据查询验证**：填入参数试跑一次，确认接口通、返回内容正确
4. **转换适配**：把接口返回的字段与流程表单字段做映射，同名不同名都在这里对齐
5. **流程中引用**：在机器人节点、表单控件或审批节点事件上挂这个函数

第 5 步有三种生效位置，选择依据：

| 挂载位置 | 生效时机 | 适用场景 |
|---------|---------|---------|
| 表单控件触发 | 用户操作该控件的瞬间 | 输入编号后自动带出其他字段 |
| 机器人节点 | 流程流转到该节点时 | 审批通过后回写业务系统 |
| 审批节点事件 | 节点进入或离开时 | 进入审批前做数据校验 |

## 二、启动流程接口（外部系统 → EKP）

老版本 EKP 主要提供 WebService，新版本同时提供 REST。

```
服务地址（WebService）：
http://<IP>:<PORT>/sys/webservice/kmReviewWebserviceService?wsdl

启动审批流程的方法：
addReview(KmReviewParamterForm webForm)
```

主要参数：

| 参数 | 类型 | 说明 |
|------|------|------|
| `docSubject` | String | 单据标题 |
| `fdTemplateId` | String | 表单模板 ID |
| `docContent` | String | 富文本内容 |
| `formValues` | String(JSON) | 流程表单数据 |
| `docStatus` | String | `"10"` 草稿 / `"20"` 待审，默认待审 |
| `docCreator` | String(JSON) | 发起人，格式见平台的人员组织架构定义说明 |
| `fdKeyword` | String(JSON) | 文档关键字 |
| `docProperty` | String(JSON) | 辅类别 |
| `flowParam` | String(JSON) | 流程参数 |
| `attachmentForms` | List | 附件列表 |

### 表单数据的组织方式

`formValues` 是 JSON，但表单原始数据的存储格式是 XML，定义在 `km_review_main.extend_data_xml` 字段里。因此开发时需要把表单控件的 ID 与取值抽出来组装成 JSON。

**明细表的格式与普通字段不同**，按列组织：

```
"明细表id.列id": ["列值1", "列值2", "列值3"]
```

每列单独组合成一个集合。这是最容易写错的地方——按行组织是行不通的。

### 附件处理

附件以 **base64** 编码传输：

```
{ fdKey: "fd_enclosure", fdFileName: "文件名", fdAttachment: <base64> }
```

大文件不适合直接塞进流程附件——base64 会让体积膨胀约三分之一，且流程表不适合存大对象。正确做法是把文件先传到文件服务器，再把链接放进 `formValues` 的某个字段。

## 三、字段映射表（联调必产出物）

联调开始前先冻结这张表，双方各持一份。用途是让"OA 控件 ID"与"业务系统列名"之间的对应关系有唯一权威来源。

```markdown
| 业务含义 | OA 控件 ID | 业务系统列名 | 类型 | 必填 | 备注 |
|---------|-----------|-------------|------|------|------|
| 单据号 | fd_change_no | change_no | 字符串 | 是 | OA 生成，全局唯一 |
| 变更类型 | fd_order_type | order_type | 整数 | 是 | 1/2/3/4 |
| 对象编号 | fd_asset_no | asset_no | 字符串 | 是 | |
| 新责任人 | fd_new_user_account | new_user_account | 字符串 | 视类型 | |
```

**纪律**：控件 ID 一旦联调完成即冻结。改名会导致接口静默收不到数据（字段为空但接口不报错），排查代价极高。

## 四、外部调用超时与失败的处理

调用外部系统时按这四层做防护：

| 层次 | 做法 |
|------|------|
| 超时设置 | 在 HTTP / WebService 客户端配置连接与读取超时，建议 5–10 秒 |
| 重试 | 针对网络抖动，最多重试 3 次，间隔递增 |
| 异步解耦 | 非实时要求的调用改为异步，投递到消息队列由独立消费者处理，避免阻塞主流程 |
| 熔断降级 | 外部系统长时间不可用时触发熔断，暂时停止调用并执行降级（返回默认值或把操作记入本地待同步表） |

**幂等性提醒**：加了重试就必须考虑重复推送。业务系统侧应对单据号建唯一约束，把重复请求拦在数据库层，而不是依赖调用方不重发。

## 五、集成类问题的定位顺序

接口不通时按这个顺序查，不要跳步：

1. 服务地址是否可达（网络层）——直接在服务器上访问 WSDL 或接口 URL
2. 认证凭据是否有效（含测试与生产环境凭据体系独立的可能）
3. 函数配置的参数是否与实际方法签名一致
4. 转换适配的字段映射是否对得上（含大小写与类型）
5. 流程是否真的流转到了挂载该函数的节点
6. 应用日志中该次调用的报错行
