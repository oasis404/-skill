# 故障排查手册

## 分层定位法

遇到问题先归层，再动手。跳层排查是浪费时间的主要原因。

| 层级 | 典型症状 | 首选动作 |
|------|---------|---------|
| 配置层 | 流程走错分支、审批人不对、字段看不到、入口找不到 | 查流程监控确定实例停在哪个节点，再回设计器核对 |
| 数据层 | 单据查不到、状态异常、报表数据对不上 | 用 `data-dictionary.md` 的语句查 `doc_status` 与表单列 |
| 接口层 | 外部系统收不到数据、自动带出的字段为空 | 按 `integration.md` 的五步顺序查 |
| 环境层 | 整站变慢、偶发失效、升级后异常 | 查应用日志与服务器资源，核对近期变更 |

**先定位置，再定原因**：不知道单子卡在哪，看日志就是盲找。

## 流程走到某个节点后卡住，不产生待办

按顺序排查：

1. **查流程实例状态**：进入后台流程监控模块，看该实例的当前节点与节点 ID，确认它到底停在哪
2. **核对节点处理人**：检查该节点的处理人来源是否配置正确。若为自定义节点，确认处理人类路径正确且类已被成功加载
3. **看节点日志**：在节点处理器中增加详细日志，重启应用后触发流程，观察代码执行到哪一步中断
4. **核对路由条件**：若该节点后有多条出口，检查条件表达式的计算结果是否符合预期。**最常见的错误是表达式引用了不存在的流程变量**

## 页面报 404

EKP 老版本基于 Struts，404 大多出在路径配置上。逐项核对：

- action 类是否继承自基类（如 `BaseAction`）
- `struts.xml` 中的 action 配置是否与实际路径一致
- JSP 页面中的表单 action 路径是否与配置匹配
- 该方法是否缺少权限注解导致被拦截

## 事务不生效

EKP 使用声明式事务管理。排查清单：

- 方法名是否匹配事务切面的表达式
- 方法是否为 `public`（非 public 方法上的事务注解不生效）
- 是否抛出了 `RuntimeException`（受检异常默认不回滚）
- 日志中是否有事务相关的报错

## 性能问题

### 列表与报表加载慢

| 层面 | 措施 |
|------|------|
| 数据库 | 用执行计划工具分析查询，检查是否缺索引、是否全表扫描；避免 `SELECT *`，只取需要的字段 |
| 查询组织 | 避免在循环中查询数据库 |
| 大字段 | 使用延迟加载 |
| 缓存 | 不常变的数据（部门树、基础代码）放入 Redis 或 EHCache，设置合理过期时间 |
| 分页 | 大数据量报表务必分页，不要一次性加载 |
| 前端 | 复杂图表可考虑后端生成图片或 SVG；确保 JS、CSS 已压缩合并 |

### 规则或校验框架引发的性能下降

开启慢查询日志，重点看规则表与规则绑定表的查询是否走了索引。可用 Profiler 类工具监控校验入口方法，关注规则查询、表达式解析、自定义校验器中的远程调用。同时监控缓存命中率——命中率过低通常意味着缓存 Key 设计不合理，或规则变更过于频繁。

### 排查"配置改动"是否引入的性能退化

把改动时间点与慢查询日志的时间分布对齐。若慢查询集中出现在改动之后，优先怀疑新增的索引缺失或条件表达式导致的全表扫描。

## 外部系统调用超时或失败

见 `integration.md` 第四节。核心四层防护：超时设置 → 重试 → 异步解耦 → 熔断降级。

## 在途单据异常

这是最需要谨慎处理的一类，因为处理动作会直接影响正在流转的业务。

**先做的事**：

1. 统计该流程当前各状态的在途数量
2. 确认异常是**单笔**还是**批量**——单笔可用特权干预，批量必须停下来找根因
3. 确认异常发生的**时间点**与最近的配置改动是否吻合

**关于配置改动的一个关键事实**：在途实例在发起时就固化了当时的流程版本。改流程模板只影响之后新发起的单据，**不能修复已经卡住的那一笔**。所以：

- 若想修复在途单据 → 用后台的特权操作干预流程，或联系发起人撤回重提
- 若想修复后续单据 → 改模板，并明确告知业务这个改动的生效边界

把这两件事混为一谈，会导致业务反复重提却仍然复现，最终怀疑系统有严重缺陷。

## 审批人无法处理

三种情形对应三种处置：

| 情形 | 处置 |
|------|------|
| 审批人临时请假 | 管理员用后台特权操作干预；或审批人事前配置"流程授权"临时委托他人 |
| 审批人已离职、账号停用 | 事后补救走特权干预；**事前预防是把审批人配成角色或公式，而非个人** |
| 审批人岗位已变更但配置未更新 | 修改节点处理人来源；若原配置为公式，检查公式依赖的字段是否仍有效 |

第三种情形的根因通常是历史遗留的硬编码配置。建议定期巡检：把"处理人来源为具体人员"的节点列出来，逐个评估是否改为角色或公式。

## 排查前的信息采集清单

任何流程类故障，先填满这张表再下判断：

```markdown
| 采集项 | 内容 | 获取位置 |
|--------|------|----------|
| 单据号 / 流程标题 | | 用户提供 |
| 流程实例 ID | | 流程监控页面或数据库 |
| 当前节点与状态 | | 后台流程监控模块 |
| doc_status 取值 | | km_review_main.doc_status |
| 涉及表单的模板 ID | | 流程模板配置页 |
| 报错时间点 | | 用户提供 |
| 应用日志中该实例的报错行 | | 应用服务器日志文件 |
| 报错前的最近一次配置改动 | | 变更记录 |
```

八项里至少要有七项，缺失项明确标为未知。信息不齐时给结论，等于把猜测包装成判断。
