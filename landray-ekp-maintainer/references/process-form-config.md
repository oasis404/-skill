# 流程与表单配置

## 整体思路：流程和表单分开做

这是配置环节最容易卡住的认知点。蓝凌里**流程**与**表单**是两类对象，分别配置，最后绑到一起：

| 对象 | 管什么 | 与谁绑定 |
|------|--------|---------|
| 流程模板 | 流转路径：几个节点、每步谁审、怎么分流 | 两者都挂到**业务类别**上，绑好用户才能在门户看到并提交 |
| 表单模板 | 单子上有哪些字段：申请人填什么、审批人看什么、数据存哪里 | 同上 |
| 业务类别 | 流程的"文件夹"，决定入口位置与提交权限 | — |

## 六步配置主线

**建分类 → 新建流程模板 → 设计节点与审批人 → 流程检测 → 设计表单模板 → 绑定并发布**

### 建分类

位置：后台管理 → 流程管理 → 类别设置。

类别决定两件事：入口在哪、谁有权限提交。层级建议不超过三层。

### 新建流程模板

位置：流程管理 → 流程模板设置，或通用流程模板设置。

两种模板的区别：**流程模板**绑在某一个分类下；**通用流程模板**可被多个分类共用——判断标准就是"会不会有第二个分类也用"。

两个容易忽略的流程选项：

| 选项 | 含义 | 建议 |
|------|------|------|
| 驳回的节点通过后直接返回本节点 | 驳回后重提，直接回到驳回他的那位审批人，不重走前面的节点 | 审批链长时开启 |
| 重新流转节点时重新计算节点处理人 | 审批人由公式/角色线/通用岗位算出时，驳回重走要不要重算 | 一般开启，与组织变动保持一致 |

### 设计节点与审批人

**审批人来源的优先级**：

| 方式 | 适用与风险 |
|------|-----------|
| 公式（动态计算） | 按表单字段算出审批人，如"由资产所属部门负责人审批"。**首选** |
| 角色 | 该角色下所有人可审，可配会签或任意一人审 |
| 部门 / 岗位 | 按组织架构定位，比具体人员稳定 |
| 矩阵组织 | 需同时按"部门 × 职能"两个维度定位时使用 |
| 角色线 / 通用岗位 | 蓝凌特有的组织抽象，复杂组织结构才需要 |
| 指定具体人员 | **风险最高**：人员调岗或离职后流程无人处理且不易发现 |

绝大多数"上线半年后流程卡住"的问题，根源都是当初把审批人硬编码成了具体某个人。

### 流程检测

位置：流程设计器工具栏 → 检测。三类常见报错：

- **节点未连线**：条件分支的每个出口都必须连，漏一个就会在实际运行到该条件时中断
- **审批人未设置**：某审批节点的处理人来源为空
- **开始或结束节点缺失**

检测通过再保存。跳过检测直接保存，流程发出去一定出问题。

### 设计表单模板

位置：表单配置 → 表单模板设置。拖控件排好版之后，三件事必须完成：

1. **字段权限**：哪个节点、哪种角色，能看到哪些字段、能改哪些字段
2. **数据存储**：表单数据默认以 XML 存于 `km_review_main.extend_data_xml`；独立表单表按 `fd_id` 关联
3. **控件 ID 命名**：这是给外部系统看的字段名，**联调完成后即冻结**

### 绑定并发布

把流程模板与表单模板绑到业务类别上。同时配好**通用编号规则**——单据号的生成格式（前缀、日期段、流水位数）在这里定义。

最后用测试账号跑完整链路：提交 → 审批 → 分支走对 → 办结，外加**驳回重提**路径。

## 节点类型速查

| 节点 | 作用 | 常见流程是否需要 |
|------|------|-----------------|
| 开始 / 结束节点 | 流程起止，必放 | 必需 |
| 审批节点 | 设定审批规则，可配会签或任意一人审 | 必需 |
| 条件分支节点 | 按条件自动分流到不同分支 | 需要分流时必需 |
| 机器人节点 | 自动执行：读写数据库、调外部接口、改文档信息 | 需外部集成时必需 |
| 抄送节点 | 推送知会，不阻塞流转 | 常需 |
| 签字节点 | 要求指定人电子签名，强留痕场景 | 可选 |
| 人工决策节点 | 人工现场选择分支 | 可选 |
| 并行分支节点 | 多分支同时推进，全部完成后汇合 | 可选 |
| 启动子流程 | 在流程中触发另一独立流程 | 可选 |
| 投票节点 | 多人投票表决 | 少见 |
| 回收子流程 / 自由子流程 | 复杂子流程编排 | 少见 |

## 表单控件速查

单行输入、多行输入、单选按钮、多选按钮、下拉菜单、复选下拉框、富文本框、日期控件、人员选择器、部门选择器、附件上传、数据填充控件、明细表。

**数据填充控件**值得单独说明：它能在用户填写某个字段后，自动从外部接口或数据库取数并填入其他字段。配置依赖集成中心的函数配置，属于要单独做的一步工作，但对"输入编号自动带出名称、当前责任人"这类体验是决定性的。

**明细表的使用边界**：用于表格式多行录入。若业务约束是"一单一对象"，用普通控件即可，套明细表会平白增加复杂度与接口解析难度。

## 条件分支的配置要点

条件表达式引用的控件 ID 必须与表单中配置的**完全一致**——大小写差一个字母，该分支就永远走不进去，而且不会报错。

```
分支 1：formValues.<控件ID> == "1"
分支 2：formValues.<控件ID> == "2"
分支 3：formValues.<控件ID> == "3"
分支 4：formValues.<控件ID> == "4"
```

一个常见错误是条件表达式引用了不存在的流程变量，此时流程会走到该节点后中断。排查方法：在流程监控里看实例停在哪个节点，再回流程设计器核对那个节点的出口条件。

## 变更管控要点

改动流程或表单配置前，先跑一次在途单据统计（见 `data-dictionary.md`），把在途数量与受影响分类报给业务确认。**在途实例固化的是发起时的流程版本**，改模板只影响之后的新单——这一点必须在改动前就跟业务讲清楚，否则业务会以为改动没生效而反复重提。
